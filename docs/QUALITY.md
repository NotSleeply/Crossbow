# Crossbow 质量交付规范

本规范适用于所有 Agent 的每次会话，与根目录 [AGENTS.md](../AGENTS.md)、
[COORDINATION.md](../COORDINATION.md)共同执行。用户在当前会话中的明确要求与授权优先。

目标是让完整操作流程可靠、界面规则一致、交付结论有证据，逐步减少用户亲自发现基础问题的负担。
用户主要决定产品方向、审美取舍和发布时机；Agent 负责主动识别关联影响，完成可独立进行的实现、验证和结果说明。

## 1. 每次会话如何开始

1. 读取上述三份规范，核对当前需求、已确认决定及未完成事项；按协作规则确认自己的分支、worktree 和认领。
2. 查看本次实际基线及相关代码，不假定聊天中的旧版本、旧截图或未合并 PR 已成为当前实现。
3. 修改前简要说明用户要完成的操作、成功/失败时的预期行为、关联范围和验证方式。把具体场景记入本次 Issue 或 PR，避免只列文件名或实现步骤。
4. 阅读与任务有关的当前规范：界面见 [UI-DESIGN.md](UI-DESIGN.md)，通知见 [NOTIFICATIONS.md](NOTIFICATIONS.md)，发布见 [RELEASE.md](RELEASE.md)，设计归档见 [设计稿档案](designs/README.md)。

同一会话不必每轮重新读取未变化的文档。上下文恢复时先使用有效摘要，仅补读缺失或已变化的部分；不重复已完成且仍适用的验证。
小改动可用一句话说明场景和影响，不增加例行审批或要求用户反复确认。

## 2. 维护一份有效的产品标准

- 用户已确认的组件、布局和交互决定，应在对应实现任务中同步到当前规范及共享组件，注明关联 Issue/PR，避免后续会话重复设计。
- 优先使用已有主题变量、按钮、输入、选择、开关、通知和布局规则。相同职责的控件不能在不同页面各自形成一套样式。
- 修改共享组件前搜索实际使用位置，检查关联页面；局部需求不能意外改变其他场景。
- 历史设计稿用于追溯；当前实现标准应明确采用哪一版。发现规范、代码与最新用户决定不一致时说明差异，并在已授权范围内同步，不默默沿用过期规则。
- 保留有操作价值的信息，检查重复提示、无效按钮、选中/焦点状态、信息层级和等待反馈。统一颜色不能消除键盘焦点、错误或禁用状态的必要区分。

## 3. 围绕场景验收

实施前选择与任务相关的场景，完成后按同一场景验证。优先级为：配置与联网可靠性、状态一致性、共享交互、视觉细节；用户明确指定的任务顺序优先。

例如，配置切换至少考虑：

- 成功时，新配置实际生效，当前配置、出口、通知和诊断对结果的描述一致。
- 失败时，旧配置及网络恢复结果明确；恢复失败不能提示已恢复。
- 等待、回滚或重启期间显示准确状态，重复点击不产生冲突操作。
- 完成后的迟到事件、旧请求和旧诊断不能覆盖新状态。

按影响选择验证范围：

| 改动 | 必须关注的范围 |
| --- | --- |
| 文案、文档及局部低影响样式 | 相关内容、链接或控件状态；不例行运行全套应用构建 |
| 页面布局 | 受影响页面的默认/最小窗口、溢出滚动、空数据及长内容 |
| 共享 UI 组件 | 实际使用位置，明暗主题、键盘/焦点、禁用/加载/错误状态；涉及文案时检查中英文 |
| 配置、内核、代理或权限 | 成功、失败、恢复、重复操作及进程/端口/权限交接；真实内核或平台环境验证不能由模拟结果代替 |
| 发布元数据与打包 | 版本一致性、既有发布门禁；实际发布状态以对应版本的已发布记录和产物为准 |

不要求每项任务遍历所有平台和状态的全排列。对受影响的组合做足检查，通过后没有新变化或失败线索就不反复扩测。
能在隔离目录和测试端口完成的原生验证由 Agent 先完成；真实用户环境的必要系统授权和最终体验确认再交给用户。

## 4. 复用生产组件预览和可复现数据

- 界面验收优先使用长期维护、直接渲染生产组件的统一预览入口，覆盖浅/深色、中英文、默认与最小窗口，以及加载、错误、无配置、长文本和大数据场景。
- 脱敏模拟只放在开发/测试边界，不进入发布代码，不操作真实订阅、代理或 TUN。端口编辑等场景应能观察是否实际提交，不能仅看截图。
- 已有稳定入口时扩展它；缺少场景时尽量复用现有生产组件原型。需要建设统一入口的工作单独建 Issue，不把整套预览基础设施重建作为每个小任务的前置条件。
- 设计稿仍按既有归档规则保存源稿、说明、实际预览及 manifest。每份证据注明代码版本、窗口尺寸、主题、语言和数据来源；新版本不覆盖旧版本。
- 浏览器或原生工具不可用时继续可独立进行的工作，保留待验项并说明限制。不得绕过访问限制，不得把旧截图或手绘效果当作当前实现的实际验收。

## 5. 如实区分完成与验证

以下状态分别记录，不能相互替代：

| 状态 | 证据与边界 |
| --- | --- |
| 实现完成 | 改动已落地；本身不证明流程正常 |
| 本地检查通过 | 注明相关构建/测试及结果，只支持其实际覆盖的结论 |
| 模拟环境验证 | 注明场景和数据来源；支持页面/交互结论，不证明真实内核、系统代理或权限交接正常 |
| 原生环境验证 | 注明对应提交/安装版本、平台和实际操作；未验证的其他平台不作推广结论 |
| PR/CI 状态 | 提交、触发、通过、失败或尚未知，只报告已知事实；PR 提交不等于合并 |
| 发布状态 | 区分版本准备、已触发发布和已正式发布；触发流程不等于发布成功 |

- 测试数量只作补充，先说明覆盖了什么场景。依赖环境变量而未启用、忽略或提前返回的真实内核用例，不能作为真实验证通过的证据。
- 旧构建的原生验收不能冒充新构建验收；可以引用仍适用的历史证据，但必须注明版本及适用范围。
- 可以提交带明确待验说明的 PR；关键场景未验证时不得称为“已全面验收”或“可放心发布”。用户明确决定带已知限制继续时，记录边界并遵循其授权，不增加重复确认流程。
- Agent 在用户看到结果前先完成自检；发现关联回归应在本次授权范围内修复，超出范围的独立问题记录 Issue 并解释影响。

## 6. 修复根因并减少复发

- 先复现或收集足够证据区分现象与原因。页面报错、真实内核、配置存储、进程、端口与权限状态应相互核对，避免只隐藏提示或盲目修改端口。
- 每次问题修复选择一项有效的防复发措施：必要的行为回归、共享组件/规范修正，或固定预览场景。
- 测试应能捕获故障行为或保护重要约束；不为可逆、低影响样式改动堆砌断言类名、CSS 数值等镜像测试。
- 验证不能靠吞掉错误、显示假成功、删除进程身份校验或修改用户其他正常设置来通过。真实配置和凭据不进入提交、截图或日志证据。

## 7. 控制成本与交付边界

- 本地完成与改动相称的必要检查后提交 PR。没有新修改、失败或未解决的风险，就复用已有有效结果。
- **默认在 PR 提交或发布流程触发后结束，不持续轮询 CI。** 不运行 `gh pr checks --watch`、`gh run watch`、循环查询、后台脚本或定时自动任务代替等待。失败后由用户通知再处理。
- 用户明确要求查看状态、处理失败或等待结果时，按该次要求执行。需要 CI 结果才能完成的后续动作，说明仍待执行；不得为省等待而绕过既有门禁或宣称完成。
- 用户已授权且平台支持的后续自动动作可以按授权设置；不自行扩大合并/发布授权。提交质量规范也遵守所有仓库改动走 PR 的规则。
- 交付简要说明结果和关联影响、实际验证、待验/限制、PR 及适用的设计稿入口。常规工作不粘贴长日志，不让用户重新阅读整个过程才能判断结果。

后续会话应先继承这些决定与证据，再推进当前任务；把“用户又指出一个问题”转化为可执行的产品标准和回归场景。
